# IRIS 垂直模型与评测实验

> 面向 InterSystems IRIS 实施、开发与运维场景，完成从官方文档治理、中文 SFT 数据构建、LoRA 对照训练到私有题库评测与错误归因的一次完整实践。

本项目关注的不是“训练分数有多高”，而是三个更贴近真实业务的问题：

1. 如何把长篇领域文档转化为质量可控的训练数据？
2. 如何判断微调模型是否真的掌握了精确领域知识？
3. 如何避免把评测规则带来的分数提升误写成模型能力？

## 项目概览

| 环节 | 实践结果 |
|---|---|

## 1. 领域数据治理

选取 InterSystems IRIS 2026.1 官方文档中的 4 份 Guide：

- Using SQL：288 页
- Using ObjectScript：210 页
- Defining and Using Classes：268 页
- Monitoring Guide：212 页

合计 978 页，覆盖 SQL、ObjectScript、类开发与监控运维。

首轮直接使用低质量 Markdown 生成了 1,002 条问答，但只有 23% 与 IRIS 领域相关。进一步检查后发现，PDF 转换产生了单词断裂、分页标记和过碎分段，模型因此脱离原文自由发挥。

改进方式：

- 修复 Markdown 排版与断词问题；
- 调整文档分段，确保单个片段包含完整语义；
- 先用单文档小样本验证，再进行全量生成；
- 使用 AI 质量评分筛除低质量数据，并再次检查领域关键词与内容相关性。

最终保留 3,100 条中文 SFT 数据，领域相关性 94%，答案平均长度 1,097 字符。数据采用 Alpaca 结构（instruction / input / output / system）。

### 数据边界

源文档属于 InterSystems 版权材料，因此数据集和模型适配器保存在私有仓库，不在本仓库公开分发。当前质量筛选主要依赖 AI 评分和规则检查，尚未形成由领域专家逐条审核的人工金标数据集。

## 2. LoRA 对照训练

使用 OLMo-3-7B-Instruct 进行 4-bit LoRA SFT，并保持数据、学习率、batch size 与训练轮次一致，只调整 LoRA 秩。

| 指标 | r=16 | r=32 |
|---|---:|---:|
| 可训练参数 | 39.98M（0.54%） | 79.95M（1.08%） |
| 平均 train loss | 1.2675 | 1.2416 |
| 最终记录 loss | 1.162 | 1.140 |
| 峰值显存 | 8.6 GB | 9.4 GB |
| 训练耗时 | 约 30 分钟 | 约 30 分钟 |

r=32 将可训练参数翻倍，但平均 loss 仅改善约 2%。在 5 个领域问题的人工观察中，r=32 虽然回答更详细，却把 IRIS global 错误描述为“进程私有”；r=16 在该知识点上反而正确。

**结论：训练 loss 的轻微改善不能替代事实正确性评测。对于 3,100 条数据，更大的 LoRA 秩没有带来与成本相称的收益，还可能放大过拟合。**

## 3. IRIS 私有题库评测

从自建数据中改写 8 道 MCQA，覆盖：

- ObjectScript 语法；
- SQL 映射与命名规则；
- 类开发与回调；
- 扩展全局引用机制。

使用同一个 DeepSeek 模型进行对照：

| 题集 | 结果 | 观察 |
|---|---:|---|
| MMLU-CS 小样本 | 5/5 | 答案分布偏斜，且存在公开题污染风险 |
| C-Eval-CS 小样本 | 5/5 | 不能据此推断真实业务能力 |
| IRIS 私有题 | 5/8 | 暴露了精确 API、命名规则和领域概念缺口 |

模型答错的选项往往“符合通用编程直觉”，但不符合 IRIS 的具体规则。这说明私有业务题比少量公开题更容易暴露领域知识边界。

需要强调：8 题只能证明评测设计与错误分析方法，样本量不足以形成稳定的模型排名结论。

## 4. 标准评测框架实验

使用 lm-eval-harness 0.4.12 在 Modal 上运行 DeepSeek 官方 API：

- 任务：GSM8K v3；
- 样本：100 / 1,319；
- 协议：5-shot CoT；
- 固定随机种子：1234；
- API 请求：100/100 成功。

| 过滤器 | Exact Match |
|---|---:|
| flexible-extract | 98% |
| strict-match | 64% |

两项分数来自同一模型、同一批题目和同一批生成结果，只是答案抽取规则不同，却相差 34 个百分点。

**因此评测报告必须同时披露框架版本、任务版本、few-shot 配置、样本量、随机种子和答案抽取方式。只写“GSM8K 98%”会把评测器收益误写成模型能力。**

## 关键结论

- 文档解析和分段质量会直接决定领域数据质量；扩大生成规模无法修复错误输入。
- AI 质量评分适合初筛，但不能替代领域专家金标和独立 held-out 测试集。
- 训练 loss 更低不代表事实更准确，模型取舍必须回到业务题集和错误类型。
- 公开 benchmark 负责横向比较，私有题库负责业务决策，两者不能相互替代。
- 分数是“模型能力 × 评测方法”的共同结果，评测协议必须与结果一起发布。

## 对 FDE 工作的价值

### 1. 从业务问题反推技术路径

目标不是为了完成一次 LoRA 训练，而是验证“IRIS 领域知识是否值得通过微调注入模型”。因此先定义实施运维场景，再筛选资料、构建数据、设计题集，最后依据事实正确性和错误类型判断方案，而不是只看训练 loss。

### 2. 把不可控生成变成受控交付

首轮 1,002 条数据只有 23% 与 IRIS 相关。通过定位 PDF 转换、分段和 Prompt 问题，先做单文档 smoke test，再全量生成，最终得到 3,100 条、94% 领域相关的数据。这套“小样本验证—质量门—全量执行—复核”的方式可以迁移到企业知识库、Agent 和工作流交付。

### 3. 用评测支持方案取舍

r=32 的可训练参数是 r=16 的两倍，但平均 loss 只改善约 2%，还引入关键事实错误。这说明技术方案不能按参数规模或单一指标决策，需要结合业务题集、失败样本、资源占用和风险边界共同判断。

### 4. 能向非模型团队解释结果

同一批 GSM8K 输出在 flexible-extract 下为 98%，strict-match 下为 64%。对业务方更重要的不是背诵两个分数，而是解释为什么会差 34 个百分点、哪个指标更贴近实际使用，以及报告还缺少哪些证据。

### 5. 保持人机边界和数据安全

源文档受版权保护，数据集和模型适配器不公开；实验不含客户数据、医院生产数据和密钥。当前数据也没有领域专家金标，因此不会把课程实验包装成可直接上线的生产模型。

## 从实验到企业方案的选型判断

如果把该实践迁移到真实客户场景，我会先建立固定业务题集和基线，再比较 Prompt、RAG 与 LoRA：

- **优先 Prompt / 工作流：** 问题主要是输出结构、步骤约束或工具调用方式；
- **优先 RAG：** 知识频繁更新、需要引用来源或必须支持审计；
- **考虑 LoRA：** 需要稳定的领域表达、行为模式或大量重复任务，并且已有足够高质量数据；
- **暂缓上线：** 没有人工金标、独立测试集和失败兜底时，不用训练 loss 代替验收结论。

这也是本项目最重要的 FDE 结论：**模型微调不是交付目标，而是可被验证、比较和否决的一种方案选项。**

## 当前边界

这是一次课程驱动的技术实践，而非生产级模型或正式商业评测报告：

- IRIS 数据集主要经过 AI 评分筛选，尚未建立人工金标；
- 7B 微调实验没有独立的大规模 held-out 业务评测集；
- 私有题库只有 8 道题，结论只能用于发现问题，不能用于模型排名；
- 本仓库不包含客户数据、医院生产数据或任何密钥。
